# WAL checkpoint strategy for the shared archive DB

turnado and the sibling `paperless.node` app share one physical SQLite file in WAL mode; neither app closes its connection during normal operation, so SQLite's own "last connection closes" full checkpoint never fires, and the default ~4MB passive-checkpoint threshold can go unhit for long stretches given this app's low, human-paced write volume. A direct file copy (backup, one-off pull, debugging) taken mid-stretch can silently miss data that only exists in the WAL — this happened for real pulling a DB copy for #14. We checked: `paperless.node` does no WAL/checkpoint management of its own (it doesn't even set `journal_mode`; it inherits WAL from turnado at the file-header level), so if either app is going to checkpoint responsibly, it has to be turnado.

Decided: turnado runs an hourly `PRAGMA wal_checkpoint(PASSIVE)` during normal uptime (non-blocking, matches the existing reminders-poll cadence), and a `SIGINT`/`SIGTERM` handler that explicitly runs `PRAGMA wal_checkpoint(TRUNCATE)` before exiting — plain `db.close()` was considered and rejected, since it only triggers SQLite's automatic checkpoint when the closing connection is the *last* one open on the file, which is never true here while `paperless.node` is running. Anyone pulling a copy of the file directly must use `sqlite3 source.db ".backup target.db"` (or checkpoint first), never a raw file copy — documented in `docs/nas-deployment-notes.md` and the on-box `NAS-NOTES.md` rather than enforced in code, since no backup script exists to change.

See [issue #43](https://github.com/uriagassi/turnado/issues/43).
